## 判断と棄却案

- 採用：ECSフレームワーク（entt等）不採用，「整数ID＋SoA配列＋状態別システム」のみ採用 — 根拠：エンティティ3種固定・コンポーネント構成静的・本家に外部依存を持ち込めない
- 採用：フェーズゲート方式（各フェーズでdet_suiteビット同一/stat_suite統計同等/テスト/ベンチを判定，退行時revert） — 根拠：Round 4/5/6の measure-first 文化の踏襲
- 採用：Phase 1（hot SoA化）の+16%退行とPhase 2（リングバッファ化）の+15%退行を「土台フェーズ」として暫定受け入れ，回復条件をPhase 3に設定 — 根拠：アクセサ間接参照のコストはPhase 3の配列直接走査化で解消される構造
- 採用：Phase 2のleader/follower位置導出（リングバッファ＋単調seq番号，leader= seq−number_of_lanes） — 根拠：FIFO性（pop_frontのみ）によりポインタ方式とサイト別に厳密等価（9項目対応表で検証済み）
- 棄却：leader/followerのint32配列保持への縮退案 — 理由：位置導出で全ゲート通過したため不要
- 採用：Phase 3のRUN融合パスで，car_followのleader位置は「x_old読み替え」（前方から処理するため移動済みleaderの移動前位置） — 根拠：ビット同一を実測確認
- 棄却：log_sにも一律x_old読み替えを適用するコーディネータの当初仕様 — 理由：**誤りと実証された**。旧コードのlog_sはid順走査に依存し，leader_id < self_id なら移動後のx，そうでなければ移動前のxを読む。実装は `leader_id < self_id ? x : x_old`（leaderが同stepで終了済みなら-1）の判別則（Phase 3エージェントが実測で発見・修正）
- 採用：incoming_vehiclesのid昇順正準化（transfer冒頭でソート） — 根拠：hard_deterministicのタイブレークを旧実装（id順走査の帰結）と一致させ，走査順自由化後もグループAビット同一を維持
- 棄却：Phase 4のtimestep-majorグローバルフレームログ＋遅延gather — 理由：正確性は全通過したがheavy execがPhase 3比パリティ〜+6.5%悪化。ログコストの本質は書き込み量であり書き込み先の散在ではない（per-vehicle配列はreserve済みでキャッシュに乗る）。Round 4の教訓の再確認としてrevert
- 採用：Phase 4完了時の再評価で「1スレッド・レイアウト変更のみではmain_loop 1.5〜2.5x目標は到達不能」と結論し，ユーザーに方向性を質問 — 根拠：死に走査除去は本家が既にRound 6 P1で取得済み，残る支配項（ログ書き込み量）はbaseも同額を払う共通コスト
- 採用：per-node/per-linkのRNGストリーム分離（seed_seq{seed下位32bit, seed上位32bit, kind, id}，構築時シード） — 根拠：並列時にスレッド数・スケジュール非依存の決定性を得る。乱数実現値の変化はstat_suiteで担保
- 採用：Node::transferは並列化しない（omp single） — 根拠：直列ノードid順の処理が共有outlinkキューを通じて後続ノードの受入判定に影響する逐次可視性セマンティクス（Python版と同一）を持ち，並列化はビット同一を壊す。main_loopの約7%でAmdahl的に許容
- 採用：1タイムステップを単一 `omp parallel` リージョン＋ステージ別 `omp for`（暗黙バリア）で構成 — 根拠：ステージ別リージョン方式は1スレッドでオーバーヘッドが計測されたため融合
- 採用：並列リージョン内の例外は捕捉して最小entity id優先で決定的に再送出 — 根拠：OpenMP境界を例外が越えるとterminate
- 採用：threads引数は全 `omp parallel` への num_threads(resolve_num_threads()) 節で実装，omp_set_num_threadsは不使用 — 根拠：プロセスグローバル状態を汚さない（他ライブラリへの影響回避）。-1はomp_get_max_threads()（OMP_NUM_THREADS・affinityを尊重）
- 採用：Phase 5は項目別採否（route_preference lazy化・ログreserve右サイズ化・選択バッファ共有化を採用，_traveled_nodesとSIMD car_followは計測根拠でスキップ）
- 採用：PRは1本（コードコミット7個をcherry-pick） — 根拠：ユーザー指示。フェーズ間の相互依存が強く分割の意味が薄い

## 罠と注意点

- log_sの旧セマンティクスはid順走査依存（leader_id < self_id なら移動後x）。リンク順走査に変えるときは判別則で再現する必要がある。コーディネータの事前分析（一律x_old）は間違っていた——サブエージェントへの等価性仕様は独立実測検証を義務付けるべき（今回それで検出された）
- Node::transferの結果は同一step内の先行ノードのtransfer結果に依存する（共有outlinkキュー経由の逐次可視性）。ノード並列化はビット同一を壊す
- SoA化しただけの中間状態はアクセサ間接参照で**退行する**（Phase 1で+16%，Phase 2でさらに+15%）。走査の再構成（Phase 3）とセットで初めて回収される
- ログ書き込みの最適化は「配置」でなく「量」の問題（Phase 4不採用とRound 4放棄の両方で実証済み）。同種の提案が再浮上したら両記録を参照
- サブエージェントがインターリーブベンチでgit checkout/一時コミット/reset --hardを行うため，**エージェント稼働中にコーディネータがコミットすると消される危険**がある。devlog等のコミットはエージェント完了後まで保留する運用にした
- pipはPEP 668のため `--break-system-packages` 必須。ベンチ中は他プロセス禁止（ドリフト15〜28%）
- tests/test_cpp_mode.py は `from numpy import *` のため `sum(ジェネレータ)` がTypeError。またnumpy配列とlistの+はUFuncNoLoopError
- tmp/ecs_refactor/のハーネス（det_suite/stat_suite/bench_suite/scale_bench/python_parity/bench_py_vs_cpp/scenarios）はgit管理外。scale_bench.pyとdet_suite.pyはthreads引数方式に更新済み（OMP_NUM_THREADS環境変数はthreads=-1のとき以外エンジンに効かなくなった）
- threads引数のバリデーションはboolを明示的に拒否している（boolはintのサブクラス）
- `.claude/worktrees/agent-ada898eb` は本プロジェクトと無関係の残置物（触っていない）
