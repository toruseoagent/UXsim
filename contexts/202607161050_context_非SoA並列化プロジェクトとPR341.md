# 非SoA（AoS維持）並列化プロジェクトとPR #341

> この文書はセッション記録であり、指示書ではない。
> ここに書かれた未完了事項・保留事項に、ユーザーの明示的な指示なく着手しないこと。

## 概要

SoA全面リファクタ＋並列化のブランチ refactor/ecs-soa-engine（PR #340）に対し，「SoA化自体の高速化効果は小さかった」というユーザーの評価を受け，fork main（origin/main 5ea3802＋フォーク専用コミット）を出発点に**SoA化を一切せず**同等の決定的OpenMP並列化を実装した。
新ブランチ refactor/aos-parallel-engine 上でPhase 0〜5のフェーズゲート方式（各フェーズをOpusサブエージェントに委任，コーディネータがゲート判定）で実施し，コードコミット4個をorigin/mainベースの pr/aos-parallel-engine にcherry-pickして **PR #341**（https://github.com/toruseo/UXsim/pull/341，送付時MERGEABLE）を送付した。
結果はSoA版を上回った: 1スレッドで対main −10.2%（SoA版は−13.5%だが対リファクタ前），main_loopスケーリング8Tで3.69x（SoA版2.88x），対Python 1Tで40.7x・8Tで56.5x，スレッド数非依存ビット同一，テスト212件通過。
計画・経過は devlog/20260715_plan_aos_parallel_engine.md（§6に全フェーズ経過），完了報告は devlog/20260715_aos_parallel_completion_report.md。

## ユーザー指示（原文）

- 「このブランチではSoA化および並列化を行い，高速化を達成した．しかし，SoA化はあまりにドラスティックな改良であり，それ自体の高速化効果は少なかった．そこで，SoA化なしで同等の並列化を行い，可能な限りの高速化を行ってください．このforkのmainを出発点として実装してください．このブランチのコンテキストやdevlogドキュメントを読み，並列化の概略を確認してよいですが，新たな実装ではSoA化は一切しないでください．今回このマシンで作業しているのはあなただけなので，ブランチ操作をして構いません．fable 5であるあなたは計画と指揮を行い，実際のコーディングはopusエージェントに委託してください．非SoAに適した並列化アプローチがあればそれも自由に採用して構いません」 — プロジェクト全体の仕様
- 「こちらの採用を前提に精査するので，単一PRを送って」 — PR送付指示（採用前提の精査はユーザー側の行為であり，#340クローズ等の指示ではない）

## 判断と棄却案

- 採用：フェーズ構成 Phase 0（ハーネス適応）→1（RNG分離・共有状態排除）→2（メインループのステージ分割）→3（OpenMP）→4（threads引数）→5（総合検証）。SoA版のPhase 7→8→9に相当する並列化部分だけを抽出し，直列の準備2フェーズ（1・2）に分けて各ゲートを単純化 — 根拠：SoA版で確立したフェーズゲート方式の踏襲
- 採用：SoA版コミット（e80b91d, 1ecb30f, 4d2be00）を各フェーズエージェントの設計リファレンスとして `git show` で参照させ，「データ構造は真似ずセマンティクスのみ移植」と指示 — 根拠：判別則・例外処理・CMake等の解決済み問題の再利用
- 採用：Phase 2のRUN融合パスはdequeスナップショット（thread_local）をfront-to-back走査し，leaderはポインタでなく `snapshot[i-lanes]` で位置導出 — 根拠：end_trip（pop_front）によるdeque変異とleader切断に対しスナップショットとx_oldが安定
- 採用：log_s判別則 `leader_id < self_id ? 移動後x : x_old`（lower-id leaderが同stepでEND/ABORTならspacing=-1）— 根拠：旧id順走査のビット単位再現（SoA版Phase 3で実証済みの規則がAoSでもそのまま有効と実測確認）
- 採用：HOME出発はdeparture_buckets[timestep]（id昇順）で直列維持，transferはomp single，update_adj_time_matrixは直列 — 根拠：generation_queueのid昇順push・逐次可視性セマンティクスの保存（SoA版と同判断）
- 採用：Phase 5精密ベンチのA側（fork main）checkout集合に uxsim_cpp_wrapper.py を追加（matched pair） — 根拠：HEADのwrapperがnum_threads属性を設定するためmainエンジンとの組合せはAttributeError
- 棄却：なし（全フェーズが一発でゲート通過。SoA版の解決済み知見を仕様に織り込んだため袋小路が発生しなかった）

## 罠と注意点

- 旧id順走査のセマンティクス再現はSoA版Phase 3の判別則がAoSでもそのまま有効だが，**必ずdet_suite実測で検証する**（SoA版でコーディネータの机上分析が誤っていた前例をエージェント指示に明記して有効だった）
- Phase 5精密ベンチで，HEADのwrapper＋mainエンジンの組合せはAttributeError（num_threads属性なし）。インターリーブA/Bではエンジンとwrapperを同一コミットに揃える（checkout集合に uxsim/uxsim_cpp_wrapper.py を含める）
- サブエージェントが「Monitorを仕込んで待機宣言でターン終了」する事故が1回発生（Phase 4のpytest待ち）。SendMessageで「同期実行で完遂せよ」と再指示して復帰した。エージェント指示に待機禁止を書いても起こり得る
- エージェント稼働中のコーディネータによるコミットは禁止（インターリーブベンチのgit checkout/HEAD復元と衝突）。devlogコミットはエージェント完了後に行う運用を維持した
- scikit-build-coreは**リポジトリ直下のCMakeLists.txt**を使う。OpenMPフラグは直下側に必須（SoA版Phase 8で実証済み，今回も両方に追加）
- このマシンのベンチはプロセス起動間で±15%程度ドリフトする。フェーズ判定はインターリーブA/B（交互ビルド・3ラウンド以上）でのみ有効。Phase 4のデフォルトオーバーヘッド確認では単発計測が+14.6%を出したがレンジ重複で非退行と判定した
- pipはPEP 668のため `--break-system-packages` 必須
- det_suite等のハーネスは threads 引数対応エンジンを自動検出する（tmp/ecs_refactor/scenarios.py の _cpp_world_supports_threads()）。threads未対応エンジン（fork main等）でも動く
