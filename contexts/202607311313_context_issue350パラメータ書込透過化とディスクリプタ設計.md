## 判断と棄却案

- 採用：ラッパー属性の書き込み透過プロパティ化（C++ 無変更） — 根拠：bindings.cpp で Node の x/y/signal_offset/flow_capacity/flow_capacity_remain/number_of_lanes、Link の主要フィールドが既に def_rw 公開済み [確認済み]
- 採用：`node.flow_capacity = v` 単独代入で flow_capacity_remain 初期化（v*DELTAT）と number_of_lanes 導出（未設定時 ceil(v/0.8)）を自動実行 — 根拠：issue #350 の提案（Python の Node.__init__ をミラー）。Python モードの posthoc は 3 属性代入が必要だが、cpp 側がより寛容になる方向の非対称は issue が明示的に許容
- 採用：未設定の node.flow_capacity / number_of_lanes は None を返す（従来 -1.0 / 0） — 根拠：Python モード互換
- 採用：Link の free_flow_speed / jam_density / jam_density_per_lane / q_star / k_star は素の Python 属性のまま（inert 記録用） — 根拠：Python モードでもシミュレーションは u/kappa/tau/w/capacity/delta を読み、これらは記録用。1:1 対応維持
- 採用：change_free_flow_speed / change_jam_density 後に q_star/k_star を更新しない — 根拠：Python 版 change_* も更新しない（従来ラッパーは更新しており Python と乖離していた）
- 採用：CppProperty ディスクリプタ（__set_name__ で属性名自動取得、owner._cpp_holder で C++ オブジェクト参照、conv で型変換、conv=None で素通し）＋ CppWorldProperty（C++ world 生成前はバッキング属性 '_'+小文字名、生成後は透過） — 根拠：1 行宣言化、性能は property と同等
- 棄却：__getattr__/__setattr__ による一括プロキシ — 理由：全属性代入がインターセプトされ車両登録などのホットパスにオーバーヘッド、インスタンス辞書との整合規律が必要でバグの温床、IDE/デバッガから不可視
- 棄却：nanobind dynamic_attr によるラッパークラス廃止 — 理由：構築時ロジック移動・オブジェクト寿命（過去に atexit/GIL クラッシュで苦労した領域）・World.__new__ ディスパッチとの整合など影響過大。薄いラッパー方針（PR #341 路線）からの構造転換になる
- 採用→棄却：Vehicle.orig/dest の Python 側キャッシュ（読み取り高速化目的） — 棄却理由：ユーザー指摘の通り raw API 直接書込や将来の C++ 内部変更（taxi モード等）でサイレントに stale になる #350 と同型のリスク。かつ計測上効果なし（ベンチ差はノイズ範囲で不変）。id 整数索引のライブ読み（self.W.NODES[cpp.id]、Vehicle.link と同パターン）に置換
- 採用→棄却：Link.length のバッキング値 _length（int 表示保持目的） — 棄却理由：同じ staleness リスク。CppProperty 化（float 読みになる）してもテスト 224 件は全通過
- 採用：World の DUO_UPDATE_TIME/WEIGHT/NOISE のみ CppWorldProperty 化 — 根拠：C++ が duo_update_weight を経路更新毎、route_choice_uncertainty を隣接行列更新毎に動的に読む（traffi.cpp:1498,1523,1268）[確認済み]。DELTAT_ROUTE が固定なのは Python も同じ
- 棄却：World の route_choice_principle 等の透過化 — 理由：C++ World が受け取っておらず対応不明。スコープ外

## ノウハウ（類似作業への転用）

- [成功] 属性をプロパティ化した直後に、その属性がループ内で読まれる箇所を cProfile（cumtime ソート＋ncalls）で確認したら、リスト内包内の 78 万回アクセス（init_after_tmax_fix の traveltime_actual 初期化が length/u を毎周読む）を特定できた。理由：素の属性→プロパティ化は 1 アクセス ~30ns→~500ns+ の変化で、ホットループでのみ顕在化する。ncalls の異常値が発生源を直接指す
- [失敗] VM 上で 0.7s 程度のベンチの 2-4% 差を 6 ラウンド程度の interleave で判定しようとしたが有意にならず（p~0.3）、傾向だけが残った。回避策：order を交互反転する 12 ラウンド paired 計測＋中央値と paired 差の両方を見る。それでも決着しない場合は cProfile で機序を特定する方が速い
- [成功] Python 実装をミラーする C++ ラッパーで転送プロパティが大量に必要な状況で、__set_name__ ディスクリプタ（owner のクラス属性で C++ ホルダー名を指定、cpp_name 省略時は Python 側属性名を流用）を使ったら 20 個超のプロパティが各 1 行になった。理由：ディスクリプタは property と同じ機構で性能劣化なし、特殊ロジック持ちだけ明示 property で残すと「素通し/特殊」の区別が宣言部で一覧できる
- [成功] ラッパーの読み取り性能が欲しい場面で、名前文字列→dict 引きではなく C++ 側の整数 id →Python 側リスト索引で解決したら文字列変換コストが消えた。理由：nanobind の str 変換は毎回コピー生成。両側の id が生成順で一致している前提は要確認
- [失敗] Python 側キャッシュ＋書込透過セッターで「エンジンは内部でこの属性を変更しない」前提の最適化をしたら、raw API 直接書込・将来機能で前提が壊れたとき読み側がサイレントに嘘をつく構造だと指摘された。回避策：計測で効果が実証されない限りキャッシュせずライブ読みで統一する。数%のオーバーヘッドは正しさと引き換えなら許容とユーザーが明言
- [失敗] 経路選択パラメータの効果検証シナリオで、目的地直前リンクの capacity_out をボトルネックにしたら渋滞が全く発生せず（トリップ終端の流出は capacity_out に拘束されない）、パラメータ非感応なテストになった。回避策：capacity_in で経路途中に入口ボトルネックを作ると Python/C++ 両モードで経路切替が発生する
- [成功] 「ノブが効くこと」を保証するテストとして、init 設定と posthoc 設定の完全一致 assert に加えて baseline（ノブ未設定）との不一致 assert を入れた。理由：一致だけだとノブが両方とも無効（vacuous）でも通る
